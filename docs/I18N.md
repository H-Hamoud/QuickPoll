# Sprachen und Darstellung

QuickPoll gibt es auf Deutsch (Standard), Englisch und Arabisch, dazu ein
helles und ein dunkles Design. Beides sind *Einstellungen der Person*, keine
Eigenschaften einer Umfrage.

## Wie die Sprache gewählt wird

1. Klick im Sprachmenü: `?lang=ar` setzt das Cookie `qp_lang` (1 Jahr) und
   leitet auf dieselbe Adresse ohne Parameter weiter. Der Wert wählt nur einen
   Eintrag aus einer festen Liste (`SUPPORTED_LOCALES`).
2. Sonst das Cookie.
3. Sonst die Browsersprache (`Accept-Language`) als erster Vorschlag.
4. Sonst Deutsch.

Für angemeldete Personen wird die Wahl zusätzlich im Konto gespeichert
(`nutzer.sprache`, `nutzer.design`):
- Beim **Login** gewinnt das Konto – die Sprache folgt auf ein neues Gerät.
- Bei einem **Wechsel** gewinnt das Cookie und wird ins Konto geschrieben.
- Nach dem **Logout** bleibt das Cookie, die Seite bleibt in der Sprache.

E-Mails werden in der Sprache des *Kontos* geschrieben, nicht in der Sprache
dessen, der ein Formular ausfüllt (siehe `forgot_password.php`).

Anonyme Teilnehmende bekommen kein Cookie, solange sie nichts umstellen.

## Übersetzen: `t()` und `plural()`

Der deutsche Text ist der Schlüssel (wie bei gettext oder Laravels
„translation strings as keys“):

```php
<?= e(t('Meine Umfragen')) ?>
<?= e(t('Hallo {name}', ['name' => $name])) ?>
<?= e(plural($n, 'Antwort', 'Antworten')) ?>
```

- `lang/en.php`, `lang/ar.php` – ein Eintrag je deutschem Text.
- `lang/de.php` – nur, was kein lesbarer Schlüssel sein kann: Pluralformen,
  Monats- und Wochentagsnamen, lange Absätze (`text.…`, `mail.…`).
- `t()` gibt **nicht escapten** Text zurück; im Template immer `e(t(…))`.
- Platzhalter `{name}` werden nach dem Nachschlagen ersetzt, eine Übersetzung
  darf sie also umstellen.

### Neuen Text hinzufügen

1. Im Code `t('Neuer deutscher Text')` schreiben.
2. In `lang/en.php` und `lang/ar.php` je eine Zeile ergänzen.
3. `php tests/run.php` – der Test meldet jeden Text ohne Übersetzung und jeden
   Platzhalter, der in einer Sprache fehlt.

### Plural

Deutsch und Englisch kennen zwei Formen, Arabisch sechs (0, 1, 2, 3–10,
11–99, Rest). `plural_category()` bildet die CLDR-Regeln nach; die Formen
stehen unter `'plurals'` in den Sprachdateien.

### Zahlen, Datum, Währung

`format_number()`, `format_percent()`, `format_money()`, `format_date()`,
`format_datetime()` in `includes/i18n.php`. Bewusst ohne die PHP-Erweiterung
`intl`, weil sie in XAMPP abgeschaltet ist.

Arabisch verwendet westliche Ziffern (0–9) – eine Entscheidung statt
gemischter Ziffernsätze. Wer ostarabische Ziffern möchte, ändert nur
`format_number()`.

## Arabisch und rechts-nach-links

- `<html lang="ar" dir="rtl">` kommt vom Server.
- Das Stylesheet benutzt nur **logische Eigenschaften**
  (`margin-inline-start`, `inset-inline-end`, `text-align: start`). Dadurch
  spiegelt sich das Layout von selbst; ein Test verbietet `left`/`right`.
- Ausnahmen stehen gesammelt im Abschnitt „10c“, Datei `css/09-rtl.css`:
  schräge Details, Icons mit Leserichtung, gespiegelte Balken.
- Diagramme mit Zeit- oder Zahlenachse bleiben links-nach-rechts, Balken und
  Skalen beginnen an der Leseseite.
- Schriften: Noto Naskh Arabic (Überschriften) und Noto Sans Arabic
  (Oberfläche), lokal ausgeliefert, per `unicode-range` nur bei Bedarf geladen.
- Kein `letter-spacing` und keine Kursive im Arabischen.
- Text von Nutzern (Titel, Fragen, Antworten) trägt `dir="auto"` bzw. `<bdi>`,
  damit deutscher Inhalt in arabischer Oberfläche lesbar bleibt.
- `ltr()` hält technische Werte wie „+12 %“ zusammen.
- `t_html()` ist `t()` für Sätze mit einem HTML-Teil (Adresse in `<bdi>`, Link): Der übersetzte Satz wird escaped, die Parameter kommen als fertiges HTML hinein.
- E-Mails setzen Adressen und Zahlen in `<bdi dir="ltr">`, damit sie im arabischen Text nicht umspringen (`mail_fill()`).

Was **nicht** übersetzt wird: Inhalte, die Nutzer schreiben (Umfragen,
Fragen, Antworten). Eine aus einer Vorlage erzeugte Umfrage entsteht in der
Sprache, in der die Person gerade arbeitet.

## Hell, Dunkel, System

- `?theme=light|dark|system` → Cookie `qp_theme` → Konto, wie bei der Sprache.
- Der Server schreibt `<html data-theme="dark">`. Bei „System“ fehlt das
  Attribut und CSS folgt `prefers-color-scheme`. Kein Inline-Skript, kein
  Aufblitzen des falschen Designs.
- Das dunkle Design ist kein Invertieren: dieselben Tokens bekommen eigene
  Werte (siehe `docs/DESIGN.md`). Die Werte stehen zweimal in `css/01-tokens.css`
  (explizit und für „System“); `tests/theme_test.php` hält sie gleich.
- Gedruckt wird immer hell.
